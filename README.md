# SIT742 2026T2 Assignment 2 — Group Forecasting Project

This repository contains the reproducible group submission for the SIT742 A2
tourism-demand forecasting project using the TULIP Lab `ISF-TDF2023` dataset.

The main deliverable is
[`SIT742-2026T2-A2-G3.ipynb`](SIT742-2026T2-A2-G3.ipynb). The assignment
requirements and supporting guides are in [`docs/`](docs/).

## Project files

```text
SIT742-2026T2-A2-G3.ipynb          Shared, graded notebook
SIT742-2026T2-A2-G3-Forecast.csv  Forecast generated by the final notebook
docs/                              Specification, rubric, guides, and starter
pyproject.toml                     Python dependencies
uv.lock                            Locked dependency versions
```

Do not rename the required notebook functions, objects, headings, or
`A2:ANSWER` markers. The marker names and order are used during assessment.

## Quick start

Install [uv](https://docs.astral.sh/uv/getting-started/installation/), clone the
repository, and run:

```bash
uv sync
uv run jupyter lab
```

Open `SIT742-2026T2-A2-G3.ipynb` in JupyterLab. The first full run downloads
the public dataset and TimesFM checkpoint, so it can take longer than later
runs. These downloads are cached locally and should not be committed.

## How we collaborate

### 1. Agree on ownership before editing

Record who is working on each section in the group chat or task board. Suggested
areas are:

- Q1–Q3 functions and validation checks
- EDA and written findings
- Q4 modelling and model comparison
- Q5 forecast generation and CSV audit
- Q6 market analysis
- Q7 video, contribution evidence, and final review

Only one person should edit the notebook at a time. Jupyter notebooks are JSON
files, so simultaneous edits often create difficult merge conflicts. If two
people must work at once, use separate branches and agree on different cells or
sections before starting.

### 2. Create a short-lived branch

Start from the latest shared branch:

```bash
git switch main
git pull
git switch -c initials/short-task-name
```

Examples: `sb/eda-findings` or `ak/q6-review`.

### 3. Make a focused change

- Edit the final notebook, not the starter notebook in `docs/`.
- Preserve all required names and `A2:ANSWER` markers.
- Keep explanations close to their relevant table or graph.
- Do not use private paths, credentials, unpublished actual values, or manual
  edits to the forecast CSV.
- Add a source and cutoff date to `external_feature_log` if external data is
  introduced.
- Avoid unrelated cell reformatting or clearing all outputs; both make notebook
  reviews and merges harder.

### 4. Check the change

For a small written or chart-caption edit, run the affected cells and inspect
their rendered output. For code or modelling changes, restart the kernel and run
the notebook from top to bottom:

```bash
uv run jupyter nbconvert --to notebook --execute --inplace \
  SIT742-2026T2-A2-G3.ipynb
```

Before committing, confirm that:

- the notebook finishes without errors;
- the Q1–Q3 toy checks pass;
- `model_summary` has exactly one selected model;
- `forecast_submission_audit["is_valid"]` is `True`;
- the forecast contains 12 months and all 20 destinations; and
- the exported CSV is generated directly from `forecast_submission_wide`.

### 5. Commit and hand off

Review the changed files before committing:

```bash
git status --short
git diff --stat
git add SIT742-2026T2-A2-G3.ipynb
git commit -m "Add EDA findings summaries"
git push -u origin initials/short-task-name
```

Include the following in the pull request or group-chat handoff:

- sections or cells changed;
- checks that were run;
- any new dependency or data source;
- any assumptions, known limitations, or follow-up work; and
- whether the forecast CSV changed.

Another group member should review the rendered notebook, not only the raw JSON
diff. Merge one notebook branch at a time, then ask the next contributor to pull
the updated shared branch before beginning.

## Resolving notebook conflicts

Do not accept an entire conflicted notebook from one side without checking it;
that can silently remove another member's work. Stop editing, coordinate with the
other contributor, and choose the correct version of each affected cell. After
resolving the conflict, rerun the notebook and verify the required markers:

```bash
rg "A2:ANSWER" SIT742-2026T2-A2-G3.ipynb
```

There should be one `START` and one `END` marker for each of Q1–Q7.

second member checks the rendered notebook against the public rubric. Confirm
